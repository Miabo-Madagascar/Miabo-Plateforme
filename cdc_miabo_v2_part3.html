3.1 Architecture Globale

Couche Client (Next.js 14 App Router)

  • Framework : Next.js 14 avec App Router, Server Components + Client Components
  • Rendu : SSR pour pages SEO-sensibles (profils tuteurs, landing) · SSG pour pages statiques · CSR pour dashboards dynamiques
  • Styling : Tailwind CSS 3.x · Shadcn/ui (remplacement UI custom v1)
  • State Management : Zustand (messaging) + TanStack Query (server state)
  • i18n : next-intl avec dictionnaires FR / MG
  • PWA : next-pwa (Service Worker, manifest, cache stratégique)
⇕

Couche API (FastAPI Python)

  • Framework : FastAPI 0.110+ · Python 3.12 · Uvicorn/Gunicorn
  • Endpoints REST : Logique métier complexe (scoring matching, calcul escrow, analytics)
  • WebSocket : Signaling pour la visioconférence (Jitsi Meet integration)
  • Tâches asynchrones : APScheduler (rappels session, rapports mensuels, nettoyage escrow)
  • Auth : Validation JWT Supabase en middleware FastAPI
  • Paiement : Intégration MVola API + Orange Money API
⇕

Couche Données (Supabase)

  • PostgreSQL 15 : 20+ tables, Row Level Security (RLS) sur toutes les tables sensibles
  • Auth : Supabase Auth (JWT, sessions, email confirm, OAuth Google)
  • Realtime : WebSocket Supabase pour messagerie, notifications, présence
  • Storage : Supabase Storage pour avatars, ressources CANOPE, fichiers messages
  • Edge Functions : Webhooks paiement Mobile Money, triggers post-session

3.3 Sécurité & Row Level Security (RLS)

Principe de sécurité fondamental
Toutes les tables Supabase ont RLS activé. Aucune table n'est accessible sans politique explicite. Les données des mineurs bénéficient d'une protection renforcée. Le backend FastAPI valide le JWT Supabase sur chaque requête.
TablePolitique RLSRègle
profilesSELECT, UPDATEUtilisateur voit/modifie uniquement son propre profil. Admin peut tout voir.
tutor_profilesSELECT public, INSERT/UPDATE propriétaireProfil validé = visible par tous. Non validé = tuteur + Admin/CANOPE seulement.
sessionsSELECT élève+tuteur+parent, INSERT élève/parentSession visible uniquement par les participants (élève, tuteur, parent lié).
messagesSELECT participants, INSERT participantMessage visible uniquement par les participants de la conversation.
paymentsSELECT payeur+tuteur+AdminTransaction visible par le payeur, tuteur bénéficiaire et Admin.
minor_profilesSELECT parent+tuteur actif+AdminDonnées élève mineur visibles uniquement par le parent lié ET tuteur avec session active.
notificationsSELECT destinataire uniquementNotification strictement privée.
admin_*SELECT/UPDATE Admin seulementTables d'administration inaccessibles sans rôle Admin.

Exemple politique RLS — table sessions

-- SELECT : visible par les participants directs
CREATE POLICY "sessions_select_participants"
ON sessions FOR SELECT
USING (
  auth.uid() = student_id
  OR auth.uid() = tutor_id
  OR auth.uid() IN (
    SELECT parent_id FROM parent_student_links
    WHERE student_id = sessions.student_id
  )
  OR EXISTS (
    SELECT 1 FROM profiles
    WHERE id = auth.uid() AND role = 'admin'
  )
);

-- INSERT : eleve ou parent uniquement
CREATE POLICY "sessions_insert_student_parent"
ON sessions FOR INSERT
WITH CHECK (
  auth.uid() = student_id
  OR auth.uid() IN (
    SELECT parent_id FROM parent_student_links
    WHERE student_id = sessions.student_id
  )
);

3.4 Progressive Web App (PWA)

Cache Strategy
  • Network First : API calls (sessions, messages)
  • Cache First : assets statiques (images, fonts, CSS)
  • Stale While Revalidate : ressources CANOPE
  • Background Sync : messages envoyés offline
Optimisations Bande Passante
  • Images WebP + lazy loading (next/image)
  • Code splitting automatique (App Router)
  • Compression Brotli/GZIP (Nginx)
  • Pagination curseur (pas d'offset SQL)
  • Debounce 300ms sur recherche tuteurs
